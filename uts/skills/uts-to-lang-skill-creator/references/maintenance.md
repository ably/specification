# 10. Maintenance

Part of the `uts-to-lang-skill-creator` skill: read [SKILL.md](../SKILL.md) first (ground rules, stop points, path convention). Links that climb out of the skill directory are spec-repo paths: resolve them against the spec clone, not against this file's installed location.

This is **Upgrade/Fix, diff-driven**: the sub-case Orient recommends at STOP-13 for a skill this procedure built, whose last run finished (state S2, [13.3](orient.md#133-state-classes)). Orient has already computed what changed since the recorded run (the State summary's "Changes" line).

The harness and the skill must stay in step with five things that change independently. Record the current state of each in the Design record ("Inputs at generation time"), so a later agent can diff against it.

| What changed | How to detect it | What to update |
|---|---|---|
| **The guide** | `git -C <spec-clone> diff <recorded-sha> -- uts/docs/writing-uts-spec-translator-skills.md uts/skills/uts-to-lang-skill-creator/` (includes staged and unstaged changes; list untracked files with `git status --porcelain -- <paths>`; for a SHA recorded before the guide reached this path, also diff its earlier path, from `git log --follow --name-only -- uts/docs/writing-uts-spec-translator-skills.md`) | Map each changed guide section to the artifacts that implement it, using the "Guide" columns in [6.1](phase-4-design-record.md#61-step-4a-draft-the-design-record) and [7.6](phase-5-generate-skill.md#76-step-5f-write-skillmd) and the gap table; update them; re-run the Phase 3 and Phase 6 checks for those artifacts |
| **The UTS docs or helper specs** | `git -C <spec-clone> diff <recorded-sha> -- uts/README.md uts/docs/ uts/objects/helpers uts/rest/unit/helpers uts/realtime/unit/helpers` | Re-run the Phase 2 assessment for the affected rows; update the harness, its smoke tests and self-tests, and its README (Known gaps), the catalogue rows and notes item 9; then re-sync the affected tests |
| **The UTS corpus** | The skill's own re-sync mode (guide [9.2](../../../docs/writing-uts-spec-translator-skills.md#92-a-re-sync-mode-should)), plus the construct scanner ([7.4](phase-5-generate-skill.md#74-step-5d-fill-the-construct-catalogue)) | New catalogue rows (stop and ask for any unmapped construct); new harness symbols the corpus uses; regenerated tests; renamed IDs handled per guide [9.3](../../../docs/writing-uts-spec-translator-skills.md#93-renamed-merged-and-added-ids) |
| **The harness itself** (a helper, mock, fixture or harness test changes) | Its smoke tests and self-tests in CI; the skill's preflight on every run | Fix a red harness test in the harness before any further translation; update the README and Known gaps; regenerate the tests whose rendering depends on the changed helper (guide 9.2) |
| **The SDK** (API, hooks, test layout, CI, capabilities) | `git -C <repo> diff <recorded-sha>` (includes staged and unstaged changes; list untracked files with `git status --porcelain -- <paths>`) over the paths the Repo profile names | Repo profile; harness and hooks; notes (the SDK source is ground truth); mapping; then a re-sync if the harness or module helpers changed shape |

**Keeping this skill's own data current.** What Orient knows about Ably's repositories and SDK names is data: update the data file, not the code.

- [`assets/eligibility.json`](../assets/eligibility.json): when Ably adds, renames or retires a repository (the deny-list, the allow-list and its capability overrides, the canonical and planned names, the definition gate's threshold).
- [`assets/capability-names.json`](../assets/capability-names.json): when an SDK adds a client alias or a door factory, or the spec renames a LiveObjects name its IDL no longer shows.

Each file starts with one `_description` (what the file is and when to update it); add a `_comment` key only where an entry would otherwise puzzle a maintainer. The scripts ignore `_` keys, check the shape, and report a malformed file as `DATA_FILE_ERROR`, naming the file and the key. Client, channel, connection, presence and LiveObjects names come from the spec clone at run time (13.8) and need no edit. After an edit, rerun Orient on a repository the change affects.

Rules for every maintenance run:

- Follow the same ground rules ([section 2](../SKILL.md#2-ground-rules)) and stop points, including the model tier ([2.8](../SKILL.md#28-model-tier-and-sub-agents)) and the last-resort rules for reference-implementation reads ([2.1](../SKILL.md#21-your-inputs)). If the guide's Patterns to avoid has changed since a recorded read, re-check that read's conclusion against it before relying on it again.
- Start from the working records; update the Repo profile and the harness design if anything they describe has changed. Orient has run and STOP-13 chose this mode. Of Phase 1, re-run the discovery rows the change touches, STOP-2 for the updated profile, and step 1e (STOP-14).
- Ask **STOP-14** again (Orient has re-run `detect_liveobjects.py`), showing the recorded D-28 and what changed in the evidence (for example, the SDK has gained the public API since a placeholder was chosen) ([section 12](liveobjects-support.md#12-liveobjects-objects-support)).
- After STOP-2 and STOP-14, before editing: copy the skill-gap-audit template into the working records if it's absent, list each detected change as an item of its section H (CH-01, CH-02, …), with the artifacts it maps to and the tests to regenerate, then ask **STOP-15**: add, skip or defer per item. The items chosen there are what permit editing the skill and harness (2.2).
- Regenerate tests through the skill; the only per-test state that survives is the list in guide 9.2 step 4 (DEVIATION gates, adapted assertions, `deviations.md` entries and, per `writing-derived-tests.md`, UTS-spec-error fail-fast placeholders until the spec is fixed) (guide [9.2](../../../docs/writing-uts-spec-translator-skills.md#92-a-re-sync-mode-should)).
- After any harness change, re-run every affected tier's smoke tests and self-tests, and regenerate the affected tests; after any script change, repeat [8.1](phase-6-validate-skill.md#81-run-the-resolver-on-every-module) and [8.2](phase-6-validate-skill.md#82-test-the-audit-itself).
- Record the new spec SHA and repo SHA in the Design record and append a changelog entry.
- If the user asks for an audit or an upgrade, or the guide's section 13 checklist changed since the recorded SHA, copy the skill-gap-audit template into the working records, take the baseline of [11.2](upgrade-existing-skill.md#112-step-u1-understand-the-existing-skill) (steps 2 and 3), then run the gap audit of [11.3](upgrade-existing-skill.md#113-step-u2-write-the-gap-audit) and STOP-15 for the affected items, rather than diffing alone.
- A capability added since the recorded D-31 (Orient's "Capability changed" line) is a change item, "capability added: <capability>". It supersedes D-31, removes the module's `unsupported` marker (and the `capabilityInapplicable` entries the new client makes runnable) and maps the new tiers, adds the module notes, turns the G-rows and checklist parts that were n/a for that capability into gaps (gap-audit sections B and C, marked "newly applicable"), adds the guide 2.7 sets for the new tiers, and asks STOP-14 again ([13.8](orient.md#138-capabilities-and-scope-stop-17-d-31)). A removed capability is its own item; tests are never deleted without asking.
- A side change (the SDK gains doors, or the user wants another side or both) is a change item, "side changed: <old> -> <new>". Ask the side question of STOP-17 again, supersede D-31, and change the scope, the mapping markers and the harness's construction path to follow the new side ([13.8](orient.md#138-capabilities-and-scope-stop-17-d-31)).
- In the generated skill, a scope change is a mapping edit (`unsupported`, `capabilityInapplicable`, `extraTests`), not a resolver change ([7.1](phase-5-generate-skill.md#71-step-5a-create-the-layout-and-the-mapping-file)).
- If STOP-14's answer differs from the recorded D-28, run [12.3](liveobjects-support.md#123-what-each-choice-adds-phase-by-phase)'s column for the new choice through Phases 2 to 6, for `objects` only, and supersede D-28.
- End with Phase 7: add a dated section to `final-report.md` (the changes detected, the artifacts updated, the checks re-run), and re-mark the acceptance-checklist rows they affect.
